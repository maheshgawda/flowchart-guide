Flowchart

A diagrammatic representation of a workflow, process, or algorithm — shown as boxes, connected by arrows, indicating order of operation.
StandardISO 5807:1985
OriginGilbreth, 1921
FlowTop → Bottom
FieldProcess design

A flowchart shows the steps of a process as boxes of various kinds, connected by arrows that mark the order in which they happen. It's a solution model for a problem, rendered so the eye can follow it.

Flowcharts are used for analyzing, designing, documenting, and managing processes or programs across fields — from software logic to factory-floor procedures. Two of the biggest benefits: flaws and bottlenecks become visible once a process is laid out this way, in a way dense prose rarely reveals.

A flowchart is cross-functional when it's split into lanes — vertical or horizontal — each representing a different team or role. A symbol placed in a lane belongs to that team's responsibility, so the chart doubles as an accountability map.

01 — symbol set

Reading the shapes

The ANSI/ISO 5807 standard fixes a small vocabulary of shapes. Each one carries a specific meaning — the geometry is the grammar of the diagram.

Terminal

Marks the start or end of a process. A stadium or rounded rectangle, usually labelled "start" or "end."

Process

A single operation that changes the value, form, or location of data. Drawn as a plain rectangle.

Decision

A conditional branch — commonly yes/no or true/false — shown as a diamond with two or more exits.

Input / Output

Data becoming available for processing, or processed data being released. Drawn as a rhomboid.

Predefined process

A named sub-process defined elsewhere — a rectangle with double-struck vertical edges.

On-page connector

A labelled circle that replaces a long, crossing line with a jump to another point on the same page.

Off-page connector

Same idea as above, but the target sits on a different page — drawn as a home-plate pentagon.

Data file

A cylinder standing in for a disk drive or stored dataset — a database or file read/write.

Document

A single printed or on-screen document — a rectangle with a wavy base edge.

02 — origin

From factory floor to source code

1921

The flow process chart

Frank and Lillian Gilbreth introduce the first structured method for documenting process flow, presented to the American Society of Mechanical Engineers as "Process Charts: First Steps in Finding the One Best Way to do Work."

1930s

Work simplification

Industrial engineer Allan H. Mogensen trains businesspeople in these tools at his Work Simplification Conferences in Lake Placid, New York — carrying the chart out of engineering and into general business use.

1947

ASME standardizes the symbols

ASME adopts a symbol set derived from Gilbreth's original work as the "ASME Standard: Operation and Flow Process Charts" — the same year Goldstine and von Neumann are independently developing flowcharts to plan computer programs.

1960s–1970

ANSI, then ISO

The American National Standards Institute sets formal standards for flowchart symbols; ISO adopts the ANSI symbol set in 1970, unifying notation internationally.

1985

ISO 5807

The current standard is published, covering documentation symbols and conventions for data, program, and system flowcharts. It was last reviewed in 2019.

1970s onward

Decline, then persistence

As interactive terminals and third-generation programming languages made source code a faster way to express algorithms, flowchart use for programming declined — but the chart persisted for process design, and UML activity diagrams and Drakon-charts carry its logic forward.

03 — classification

Four kinds of control

Sterneckert (2003) grouped flowcharts by what they control, rather than by what flows through them — a distinction other authors have sliced differently, but this framing is the most widely cited.

01

Document flowchart

Shows the controls governing a document's path through a system — who touches it, in what order.

02

Data flowchart

Shows the controls over how data moves through a system, independent of the physical documents carrying it.

03

System flowchart

Shows controls at the physical or resource level — hardware, storage, and the machinery a process runs on.

04

Program flowchart

Shows the control logic inside a single program running within a larger system.

Other authors count differently: Veronis (1978) named system, general, and detailed flowcharts; Fryman (2001) added decision, logic, and product flowcharts to the list. The vocabulary varies by author, but the underlying idea — a flow graph abstracting away node types and content — stays the same.

04 — beyond the basics

Parallel work, and what the chart doesn't capture

For processes that fork into independent branches, a horizontal bar marks the split and rejoin: at a fork, one incoming path becomes two or more outgoing ones; at a join, every incoming path must finish before the single outgoing path continues.

A plain drawing program can produce a flowchart, but it has no underlying data model — nothing to share with a database or a project-management tool. Purpose-built software can generate flowcharts directly from source code or from a flowchart description language instead of freehand drawing.

Flowcharts also have a known limit: they don't suit recursive programming well, which is part of why source code and UML activity diagrams overtook them for describing algorithms, even as the chart remained the clearer tool for laying out a business process end to end.
